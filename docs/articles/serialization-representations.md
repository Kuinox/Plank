# Serialization representations

Decimal representation dispatch is defined in `Plank.InternalGen/DecimalRepresentationGenerator.cs`.
Each manifest entry supplies a physical type, its width or variable-length framing, and both
conversion directions. The generator emits concrete plain writer loops, plain reader dispatch,
physical Bloom hashing, and inverse-conversion overloads for retained append values. Schema
validation uses the same manifest's supported physical types.

The numerical conversion algorithms remain in `ParquetDecimalConverter`. Encodings such as
delta and byte-stream split continue to use those scalar conversion kernels directly. The
manifest does not introduce a runtime codec registry, virtual calls, intermediate physical
arrays, or an additional pass over values. Generated writer helpers inline into the existing
specialized callers. Reference-type binary loops remain concrete because static interface
dispatch does not reliably inline under shared generics.

Optional binary plain encoding is generated by `BinaryRepresentationGenerator` from one
fixed-width representation list. The array and memory paths receive the same framing
predicate and width expression. Their concrete loops and method boundaries retain the
original layout: splitting those methods changed JIT code and regressed binary throughput.

When changing a decimal representation, update its manifest entry and its conversion kernels.
The generated consumers must compile against both directions. Keep the independent physical
byte/hash cases in `RepresentationContractTests` in sync; those expectations deliberately use
`BigInteger` and explicit endian writes rather than the production converters. The same test
class checks binary framing across row shapes, known/unknown sizes, empty and all-null pages,
boundary counts, and invalid fixed widths.

`DecimalRepresentationE2ETests` covers required and optional decimal columns, plain and
dictionary encodings, V1/V2 pages, multiple pages, and all-null columns. Parquet.Net reads the
INT32, INT64 and fixed-length cases independently. Its current BYTE_ARRAY decimal limitation
is covered by independent byte and hash expectations instead. The decimal append and Bloom
regression tests cover retained values and Bloom membership.

For performance validation, compare Release builds on the same runtime and machine, with
reused buffers and warmed methods. Inspect JIT output as well as elapsed time: a new helper
must not add work to a per-value loop. Measure allocations separately and compare against a
saved pre-change assembly. A single timing sample cannot establish equivalent throughput.

This is the first migration: other logical types still use the existing handwritten dispatch.
Migrate those by representation while retaining their specialized bulk kernels and measuring
the affected paths.
